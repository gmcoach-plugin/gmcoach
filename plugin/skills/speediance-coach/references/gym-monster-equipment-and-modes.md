# Inwentarz, ruchy i tryby GM Coach

Dokument łączy wymagania ćwiczeń zwrócone przez Speediance z odrębnym stanem wyposażenia posiadanego przez użytkownika. Zestawy, dodatki, firmware i opcje zależą od modelu, regionu, pakietu i ćwiczenia. Oficjalna strona Speediance pokazuje różne konfiguracje akcesoriów oraz tryby; nie potwierdza, że są dostępne w każdym zestawie/ćwiczeniu. Katalog ćwiczeń pobierany bezpośrednio z API zwraca wymagane akcesoria z pola `accessories` w metadanych działania. To wymaganie ćwiczenia, nie inwentarz użytkownika. [Speediance Gym Monster](https://www.speediance.com/products/speediance-home-gym) · [Instrukcje Speediance](https://eu.speediance.com/en/pages/user-manual).

## Pytania do inwentaryzacji

1. Wywołaj `speediance_get_owned_equipment` dla wybranego profilu. Wynik rozdziela globalny `catalog` od jawnej listy `ownedAccessories` zwróconej przez API tego profilu. Odpowiedź `/app/accessories/list` jest wyłącznie katalogiem wszystkich akcesoriów; sama w sobie nie potwierdza, że użytkownik cokolwiek z tej listy posiada.
2. Pobierz ćwiczenia narzędziem `speediance_search_exercises`. Każde ćwiczenie ma `requiredAccessories` odczytane z własnych metadanych (`accessories`) oraz `equipmentStatus`. Jeśli API szczegółów zwróci `mainMuscleGroupName`, używaj go wyłącznie przy `mainMuscleGroupStatus: available`; nie zakładaj na tej podstawie mięśni drugorzędnych. Obecny kontrakt nie potwierdza wysokości linek ani kąta ławki. Jeśli API zwróciło wymagane akcesoria, ale inwentarz jest znany, `availability` może wskazać `available` lub `missing-accessory`. Jeśli własność jest nieznana, wyniki pozostają widoczne, `availability` ma wartość `unknown`, a narzędzie zwraca ostrzeżenie; domyślne `owned_only: true` nie ukrywa ćwiczeń przy nieznanym inwentarzu.
3. Publiczne API nie gwarantuje, że konto zwróci listę posiadanych akcesoriów. `/app/accessories/list` jest katalogiem globalnym; nie traktuj go jako listy własności. Gdy API nie zwraca jawnej listy, zapytaj użytkownika, co ma, zapisz `ownedEquipmentNames` i `equipmentOwnershipStatus` w lokalnym profilu trenerskim i odróżniaj to źródło od danych konta. Lista `complete` potwierdza także brak niewymienionych elementów; `partial` potwierdza tylko wymienione pozycje. `equipmentStatus: no-accessory-listed` oznacza, że metadane ruchu nie wymieniają akcesorium, a `unknown` oznacza brak wiarygodnego źródła inwentarza.
4. GM Coach działa samodzielnie, bez importowania danych ani konfiguracji z innych pluginów. Jeśli konkretne ćwiczenie wymaga akcesorium, a jego obecność nie jest potwierdzona ani przez konto, ani przez użytkownika, zapytaj o ten element przed włączeniem ruchu albo wybierz alternatywę z potwierdzonym sprzętem.

Ustal model GM tylko na podstawie profilu, API lub odpowiedzi użytkownika; urządzenie nie jest autodetekowane przez listę akcesoriów. Użytkownika pytaj o pozostałe warunki wpływające na bezpieczną konfigurację (np. przestrzeń, ustawienie ciała, limit ruchu, tryby widoczne na urządzeniu). Nie zakładaj, że opcja z marketingowej strony jest w jego pakiecie.

## Katalog ćwiczeń, identyfikatory i jednostki

- Przed wyborem ćwiczeń pobierz aktualny katalog przez `speediance_search_exercises` dla aktywnego profilu/`deviceType`. `id`/`groupId` i `title` z odpowiedzi są kanonicznym źródłem identyfikatora i nazwy ruchu w tej sesji. Nie myl ID grupy ćwiczenia (`groupId`) z ID wariantu API (`actionLibraryId`) ani ID presetu (`templatePresetId`); to różne pola i nie są zamienne. `speediance_preview_program` dodatkowo weryfikuje, czy ID ćwiczenia i nazwa pasują do katalogu. Nie twórz ręcznych, zapamiętanych map ID, nie przepisuj ID z innego modelu/regionu ani nie zakładaj, że identyfikator stały w starszej wersji pozostaje ważny.
- `mainMuscleGroupName` pochodzi z detali `/app/actionLibraryGroup/list`; pole opisuje jedną główną grupę mięśniową. Metadane brane są z aktualnej odpowiedzi API, nie z nazwy ćwiczenia. Kiedy `mainMuscleGroupStatus` nie wynosi `available`, pozostaw grupę mięśniową nieokreśloną. Katalog nie potwierdza mięśni pomocniczych, wysokości linek ani kąta ławki.
- Jeśli celem jest sprawdzenie „wszystkich ćwiczeń”, użyj pustego `query` i limitu do 200 oraz sprawdź `count`, `totalMatching`, `catalogStatus`, `incompleteCategories` i `catalogWarning`. Jeśli `totalMatching` przekracza `count`, wykonaj dodatkowe, węższe wyszukiwania po nazwach/kategoriach obecnych w katalogu; narzędzie nie gwarantuje paginacji. Przy częściowym/uciętym katalogu nie deklaruj pełnego pokrycia. Dobieraj wyłącznie pozycje zwrócone z bieżącego katalogu; jeśli brak konkretnego ruchu, pokaż to jako niepotwierdzone lub niedostępne zamiast zgadywać jego ID.
- Rozstrzygaj jednostkę według znormalizowanych pól GM Coach. Dla zapisanych szablonów odczytany `completionMethod` `0` lub `2` oznacza sekundy, a `1` powtórzenia (obserwowane w danych Speediance); format zapisu klienta referencyjnego to `1` powtórzenia i `2` sekundy. To mapowanie zależy od endpointu i nie jest oficjalnym kontraktem Speediance. `countType=2` może wystąpić przy obu jednostkach; nawet błędna długość listy countType nie unieważnia poprawnej jawnej jednostki ani rozpoznanego `completionMethod`; `selectCompletionMethod` oraz katalogowy `countType` są metadanymi, a nie dawką serii. Dla historii użyj zwróconych znormalizowanych `gmCoachSessionSummary` i `gmCoachTimeInterpretation`, uwzględniających kontekst endpointu: wspólne kody 0/2 oznaczają sekundy, 1 powtórzenia; kod 5 oznacza czas wyłącznie dla potwierdzonego Vita dataStatType=6 w zakończonej historii (wykonane powtórzenia pozostają osobną metryką). Konflikt z jawnym `unit`, lista jednostek lub completionMethod niezgodna z liczbą serii albo nieobsługiwany kod completionMethod daje `unit: "unknown"`; pytaj tylko, jeśli interpretacja jest potrzebna do żądanej zmiany. W nowym planie trener sam wybiera jawne `unit: "reps"` albo `unit: "sec"`.
- Przy planowaniu cardio wybieraj wyłącznie ruchy cardio faktycznie zwrócone z bieżącego katalogu dla urządzenia, a wymagane akcesoria zestawiaj z inwentarzem jawnie zwróconym przez konto Speediance albo potwierdzonym przez użytkownika. Sam globalny katalog akcesoriów, kategoria lub nazwa ćwiczenia nie dowodzą, że użytkownik ma przystawkę ani że urządzenie obsługuje daną funkcję.
- API programu nie ma potwierdzonego osobnego pola per-set intensywności cardio ani pól tętna, prędkości/kadencji, watów, nachylenia czy ciągłej rampy. Dla katalogowych ćwiczeń Row/Ski GM Coach zapisuje jawny czas w sekundach, a cel 1–10 koduje w tagu nazwy programu zgodnie z klientem referencyjnym (np. `🚣5,7`). Pokaż użytkownikowi dokładną nazwę przed zgodą. Ten tag jest widoczną wskazówką dla użytkownika, nie natywnym ustawieniem oporu urządzenia. Nie twierdź, że tryb interwałowy/rampowy, HR, kadencja, moc lub nachylenie zadziała natywnie, jeśli nie ma potwierdzenia w schemacie i odczycie zwrotnym.

## Serie dynamiczne, izometryczne i cardio mierzone czasem

Coach może dobierać ćwiczenia wykonywane na czas — dynamiczne lub izometryczne, z masą ciała albo z obciążeniem — gdy taki sposób pracy ma lepsze uzasadnienie dla celu i całego planu, a użytkownik może wykonać go bezpiecznie. Każdy czas, intensywność, liczba serii, przerwa i progresja muszą mieć uzasadnienie w aktualnych badaniach dla odpowiedniej populacji i celu; szczegóły oraz zakres dowodów opisuje `../../training-science/references/resistance-training-evidence.md`. Nie traktuj serii czasowej jak powtórzeniowej ani nie konwertuj sekund na reps, RIR, Smart RM lub %1RM.

- Nazwij rodzaj pracy: statyczny hold/izometria albo ciągły ruch dynamiczny. Dla cardio nazwij tryb wysiłku (np. ciągły/interwałowy) wyłącznie jako zalecenie treningowe; nie przedstawiaj go jako opcji urządzenia, dopóki nie potwierdzi go aktualny schemat.
- Dla czasu ustaw jawne `unit: "sec"` i `durationSeconds`; dla powtórzeń `unit: "reps"` i `reps`. W odczytanej historii/szablonie stosuj jednoznaczne `unit` zwrócone przez GM Coach także przy `unitResolution: "api-code-inference"`; nie wymagaj dodatkowego potwierdzenia użytkownika. Jeśli wynik nadal jest `unknown`, nie przypisuj jednostki na podstawie samej wartości liczbowej.
- W serii czasowej nie wyliczaj obciążenia z sekund, RIR ani RM. Smart RM i `profile-auto` wymagają powtórzeń, więc nie przypisuj ich serii czasowej. Zapisz czas bez obciążenia albo użyj ręcznych kg tylko na wyraźną prośbę, gdy API zachowuje czas i ciężar w jednej serii; w przeciwnym razie pokaż ograniczenie i wybierz wersję bez obciążenia lub instrukcję ręczną.
- Trening czasowy z obciążeniem wybierz tylko wtedy, gdy uzasadniają go cel i badania, znasz bezpieczne obciążenie, a API potrafi zachować jednostkę i obciążenie w tym samym ćwiczeniu. Stałe kg wymagają wyraźnej prośby i wiarygodnej wartości; jeśli Coach nie ma potwierdzonej ścieżki zapisu, pokaż ten element jako instrukcję ręczną. Nie zamieniaj pracy czasowej na reps/RIR/RM ani nie przedstawiaj wartości z lokalnej krzywej dla powtórzeń jako obciążenia czasowego.
- Przy izometrii dopasuj kąt, długość mięśnia, czas i wysiłek do celu; badania wykazują specyficzne adaptacje, a nie ogólną przewagę nad ruchem dynamicznym. Przy pracy dynamicznej liczba sekund to czas ciągłego wysiłku, nie tempo pojedynczego powtórzenia. Kończ serię, gdy pozycja/kontrola się pogarsza albo pojawia się ból; nie zwiększaj czasu kosztem techniki.
- Gdy wpis czasu zostanie zakodowany przez reverse-engineered API, ale nie ma odczytu potwierdzającego urządzenie, nazwij to granicą nieoficjalnego kodowania. Serializer używa pól `setsAndReps` i `completionMethod`, których semantyka czasu nie jest zweryfikowana na urządzeniu; widoczny wynik podglądu sam nie potwierdza odtworzenia czasu ani wybranego obciążenia.

Cardio na Gym Monster wymaga dodatkowego sprawdzenia: włącz do planu tylko ruch z live catalog dla bieżącego typu urządzenia oraz wszystkie wymagane, potwierdzone akcesoria. Dla Row/Ski podaj czas w sekundach i intensywność 1–10 per set; GM Coach zapisze ją jako tag w tytule programu i ujawni ten tytuł przed zgodą. Dopasuj ciągły wysiłek albo interwały do celu aerobowego, czasu, kondycji, historii, zdrowia i regeneracji oraz badań; wysiłek wysoki nie jest domyślną/obowiązkową opcją. Jeśli katalog nie zwraca cardio albo nie potwierdza jego sprzętu, zaoferuj plan cardio poza maszyną jako odrębną, ręczną propozycję, bez fikcyjnego Gym Monster ID. Jeśli potrzebne tempo, kadencja, waty, tętno, nachylenie, zmiana oporu w czasie lub ramp profile nie mają potwierdzonych pól, opisz dokładne ograniczenie i nie ogłaszaj ich zapisanymi.

## Pokrycie treningu całego ciała

Po inwentaryzacji twórz mapę ruchów dostępnych u tej osoby, np.:

| Wzorzec | Możliwe kategorie do sprawdzenia w katalogu i zestawie |
|---|---|
| Pchanie poziome/pionowe | Warianty wyciskania lub press na uchwytach/drążku i odpowiednim podparciu; alternatywy z masą ciała na macie |
| Przyciąganie poziome/pionowe | Wiosłowanie, przyciąganie z góry, jednostronne i obustronne, zależnie od położenia linek i osprzętu |
| Dominacja kolana | Przysiad, wykrok/step-up i warianty jednostronne tylko jeśli konfiguracja, zakres ruchu i osprzęt są potwierdzone |
| Zawias biodrowy/pośladki | Martwy ciąg i jego warianty, ruchy wyprostu biodra, most/hip thrust, uginanie nogi/pas na kostkę, jeśli urządzenie i katalog je obsługują |
| Barki i ramiona | Uniesienia, wyprosty i uginania z uchwytami, liną lub innym dostępnym osprzętem |
| Tułów/core | Zgięcie/wyprost, antywyprost, antyrotacja i stabilizacja na wyciągu/akcesorium; warianty z masą ciała i obciążeniem; ćwiczenia na macie i poza nią |
| Kondycja/ruch cykliczny | Rower, wioślarz, ski lub marsz/kondycja tylko gdy dana przystawka jest rzeczywiście dostępna i obsługiwana |
| Mobilność/rozgrzewka | Ruchy bez obciążenia na macie lub przestrzeni użytkownika, dopasowane do treningu i ograniczeń |

To kategorie, nie obietnica funkcji konkretnego urządzenia. Wybór ćwiczeń ogranicza się do aktualnego katalogu, `requiredAccessories`, potwierdzonej dostępności sprzętu, instrukcji urządzenia, doświadczenia użytkownika i bezbolesnego zakresu. Jeśli wyposażenie jest `unknown`, nie przedstawiaj ruchu wymagającego nieznanego dodatku jako potwierdzenie dostępnego sprzętu.

## Brzuch, core i ruchy na macie

Nie ograniczaj treningu brzucha do maty ani wyłącznie do klasycznych skłonów. Zależnie od celu i możliwości wybieraj spośród ćwiczeń core z linek/uchwytów/liny/pasa, ruchów antyrotacyjnych, wariantów z obciążeniem, stabilizacji, pracy jednostronnej i ćwiczeń z masą ciała. Do przykładów ruchów na macie całego ciała mogą należeć pompki, mosty/unoszenia bioder, dead bug, bird dog, podpory, mobilizacja bioder/barków i proste ruchy ogólnorozwojowe. Te przykłady nie muszą być ćwiczeniami Speediance w katalogu.

Dobieraj kombinację na podstawie konkretnego celu (siła tułowia, hipertrofia, stabilizacja, kondycja), historii, tolerancji i całego tygodniowego obciążenia. Jeśli użytkownik chce rozwijać mięśnie brzucha, progresuj obciążenie/powtórzenia lub trudność, a nie tylko wydłużaj podpór. Nie obiecuj redukcji tłuszczu z wybranego miejsca.

## Superserie bez przekładania wysokości i osprzętu

Użytkownik chce, by w parze superserii nie trzeba było regulować wysokości linek ani zmieniać uchwytów/sprzętu; dopuszcza łączenie z matą. Obowiązują następujące reguły:

1. Wybieraj tę samą wysokość linki i ten sam zaczep/uchwyt dla wszystkich ruchów z linką w parze. Jeśli ruch drugi wymaga innej wysokości, uchwytu, drążka, ławki lub przystawki, nie łącz ich w jedną superserię.
2. Do ruchu z linką można dobrać ruch na macie/masą ciała. Ruch matowy może trenować brzuch/core lub inną grupę. Nie włączaj automatycznie zmiany sprzętu jako domyślnej „superserii”.
3. Jeśli między ruchami trzeba bezpiecznie odłożyć uchwyty i przejść na matę, upewnij się, że linki/osprzęt nie pozostają napięte w przejściu ani nie stwarzają ryzyka zaczepienia; postępuj zgodnie z instrukcją GM. Gdy nie można bezpiecznie przejść bez zmiany konfiguracji, wykonuj ruchy osobno.
4. Używaj superserii tylko wtedy, gdy użytkownik ich chce i pomagają w czasie/organizacji bez pogorszenia celu, jakości, bezpieczeństwa lub regeneracji. Preferuj pary, w których drugi ruch nie obniża jakości pierwszego ani całej sesji. Nie superseruj priorytetowego ciężkiego ruchu tylko po to, by skrócić plan.
5. Podaj ruch A → ruch B, konfigurację, powtórzenia/czas, przerwę po obu ruchach i czas do kolejnej rundy. Jeśli oszczędność czasu jest mała lub użytkownik musi często zmieniać pozycję, zwykłe serie są lepszym wyborem.

GM Coach zapisuje parę jako naprzemienne pojedyncze wiersze A/B, z minimalną przerwą przejściową i odpoczynkiem po ostatnim ćwiczeniu rundy. Serwer wymaga równych serii, sąsiednich ćwiczeń i potwierdzonego wspólnego ustawienia; bodyweight z maty może być parą dla jednego ustawienia maszyny. API nie zwraca osobnego identyfikatora grupy, więc nie zakładaj, że aplikacja Speediance pokaże formalną etykietę superserii. Kolejność i przerwy można zweryfikować w odczycie zwrotnym.

## Customize, nazwany preset i progresja obciążenia

Domyślnie zapisuj oporowe serie powtórzeniowe jako maszynowy Smart RM. Publiczne UI klienta referencyjnego używa globalnych presetów z zakresami reps: Gain Muscle ID 1 (8–12), Stamina ID 3 (13–20), Strength ID 5 (2–8). Dobierz preset do celu, a dokładny wariant ćwiczenia (`actionLibraryId`) wybierz niezależnie z API; ID presetu nie jest potwierdzane przez metadane wariantu. Dla hipertrofii wybierz Gain Muscle, także przy 12 reps. Przy edycji starego szablonu podaj jawny cel, nie dziedzicz dawnego presetu. Nie proś modelu ani użytkownika o bezpośredni `rmLevel`. Publiczny referencyjny interfejs pokazuje zakresy i wartość startową presetu; GM Coach używa tej wartości wyłącznie jako ukrytego pola adaptera, gdy narzędzie nie poda RM. Payload zawiera `weights=3.5` oraz `counterweight`/`counterweight2`, ale nie ujawnia algorytmu firmware ani nie dowodzi, że aktywny MCP klient referencyjny serializuje go identycznie. Nie wyprowadzaj licznika z reps/RIR/%1RM i nie pokazuj 3.5 ani licznika jako ciężaru lub procentu. Niepewny cel, jednostka serii lub wariant blokuje zapis; nie zmieniaj celu ani powtórzeń, żeby dopasować inny preset. Statyczny klient referencyjny `Customize`/GM Coach `profile-auto` wybieraj tylko po jawnej prośbie. Wymaga kotwicy 1RM/e1RM dopasowanej do groupId albo potwierdzonej serii roboczej oraz jednostki konta. Jeśli sama kotwica zawiera actionLibraryId, musi on pasować; w przeciwnym razie potwierdź wariant osobno w katalogu. Nie wybieraj kotwicy z surowej historii, nieopisanego `maxWeight` ani pierwszej statystyki. Przy braku lub konflikcie zatrzymaj statyczną ścieżkę i zapytaj. Ukryj statyczne kg/lb w podglądzie do czasu prośby. Ręczne stałe kg wymagają wyraźnego życzenia i wartości dla każdej serii.

Limity presetów są walidacją oprogramowania, a nie zaleceniem treningowym. Reps, RIR i przerwy dobieraj z badań do celu i osoby. Serie czasowe pozostają w sekundach i nie używają Smart RM; bodyweight oraz cardio korzystają z osobnych ścieżek.

- Jawnie wybrany preset Gain Muscle: 8–12 planowanych powtórzeń; UI klienta referencyjnego pokazuje przerwy 45–120 s.
- Jawnie wybrany preset Stamina: 13–20 planowanych powtórzeń; UI klienta referencyjnego pokazuje przerwy 30–180 s.
- Jawnie wybrany preset Strength: 2–8 planowanych powtórzeń; UI klienta referencyjnego pokazuje przerwy 60–180 s.
- Poziomy RM zapisuj w potwierdzonym wire zakresie 1–20. Przykładowe wartości suwaka widoczne w UI nie są ograniczeniem wire potwierdzonym dla API; nie wyprowadzaj poziomu z reps/RIR ani nie zakładaj mapowania na %1RM.

Gdy użytkownik wyraźnie wybiera `Customize`/`profile-auto`, wymagaj jednoznacznego, zweryfikowanego 1RM/e1RM dopasowanego do groupId albo jawnie potwierdzonej bieżącej serii roboczej oraz jednostki konta. Kotwica z actionLibraryId zawęża zakres do tego wariantu; kotwica grupowa nie wymaga wariantowego 1RM. Gdy statystyka jest bez daty, są równorzędne kandydaty albo jednostka jest nieznana, nie zgaduj. Od wersji 1.0.64 GM Coach zawiera pełną uniwersalną tabelę klienta referencyjnego dla 1–20 powtórzeń, a nie ograniczenie do trzech przykładów 5/8/12. Używaj adaptera serwera bez interpolacji i ekstrapolacji. Obserwowane assessment-based suggest_load wybiera min(reps+1,20) i zaokrąglenie pełnej jednostki konta zgodne z nearest-even; odd-half ties i lb mają tylko testy syntetyczne. To dane oprogramowania, nie indywidualna krzywa VBT ani dowód fizycznego działania firmware. Statyczny serializer obsługuje jednostkę wire osobno; nie omijaj adaptera własnym przeliczeniem weights.

W Smart RM zachowuj planowane reps i celowy RIR jako widoczne, niezależne elementy dawki. Poziom RM jest ukrytym polem technicznym serializera, ustawionym na publiczną wartość startową danego presetu, jeśli nie podano go wewnętrznie. Nie wyliczaj go z reps, RIR ani `%1RM`; nie utożsamiaj go z `%1RM` ani kilogramami.

Smart RM nie wymaga jednostki kg/lb, lokalnej kotwicy ani odczytu statystyk 1RM przed zapisaniem nazwanego presetu. Wariant potwierdź osobno w katalogu. Maszyna może wyznaczać i aktualizować ciężar podczas treningu; API szablonu nie dowodzi fizycznego obciążenia. Jawnie wybrane `Customize`/`profile-auto` zapisuje statyczne `weights` w potwierdzonej jednostce konta i wymaga zweryfikowanej kotwicy; nie jest to ręczne fixed-kg. Nie pokazuj bezwzględnych kg/lb w podglądzie bez prośby. Zapisane `weights` nie dowodzą, że urządzenie automatycznie przeliczy obciążenie po późniejszej zmianie profilu. Odczyt API potwierdza pola, nie działanie firmware ani zachowanie na każdym modelu.

1. Przy oporowych seriach powtórzeniowych potwierdź dokładny wariant w katalogu. Na GM1 wybierz globalny preset według celu: Gain Muscle=1, Stamina=3, Strength=5; nie wymagaj mapy presetu do `actionLibraryId`. `speediance_get_exercise_presets` wywołuj przy nieznanym presetcie lub diagnostyce mapowania, nie rutynowo dla tych trzech nazw. Nie myl ID ćwiczenia, wariantu ani presetu.
2. Smart RM jest domyślny: cel hipertrofia→Gain Muscle ID 1, siła→Strength ID 5, wytrzymałość→Stamina ID 3; zachowaj reps i RIR jako osobne wartości planu. Wariant ćwiczenia wybierz oddzielnie z API. Serwer używa publicznej wartości startowej presetu jako ukrytego RM adaptera, jeśli nie podano jej wewnętrznie. Użyj referencyjnego formatu `weights=3.5` i `counterweight`/`counterweight2`; nie pokazuj technicznego licznika, nie przypisuj go do kg ani %1RM i nie wyliczaj go z reps/RIR.
3. klient referencyjny `Customize`/GM Coach `profile-auto` wybieraj tylko po jawnej prośbie o statyczne obciążenia. Wymagaj dokładnej kotwicy 1RM/e1RM lub potwierdzonej serii roboczej oraz jednostki konta; brak lub niepewność zatrzymuje zapis.
4. Manualne stałe kg wolno włączyć wyłącznie po wyraźnej prośbie użytkownika i tylko z wartością dla każdej serii; nie wyprowadzaj ich automatycznie z historii.
5. Ćwiczenia wyłącznie z masą ciała oznacz `loadType: "bodyweight"`; nie podawaj im presetu ani obciążenia. Serie czasowe zachowują sekundy, a cardio ma osobną ścieżkę. Odczyt zwrotny potwierdza zapisane wartości, nie obliczenie oporu przez firmware.
6. Zapis korzysta z nieoficjalnego reverse-engineered API. Podgląd nie potwierdza faktycznego oporu. Po treningu oceniaj wykonane powtórzenia, jakość ruchu, zadeklarowany RIR, ból i regenerację; nie zakładaj, że historia zawiera liczbowy 1RM.

Przy każdej technice intensyfikacyjnej sprawdź cel, poziom, tolerancję, regenerację i ograniczenia zdrowotne. Nie dodawaj drop-setów, rest-pause, powtórzeń z pauzą/tempa ani innych metod jako ozdobnika lub domyślnej progresji. API planu nie ma odrębnych pól opisujących takie protokoły; można je przybliżyć wyłącznie wierszami serii (krótka przerwa, cel reps/RIR na wiersz; ciężar dobiera Smart RM) według instructions-cycle.md, a decyzja intensity_techniques jest wtedy applied, inaczej not_used. Nie umieszczaj takich instrukcji wykonawczych w ćwiczeniach ani notatkach, aby omijać bramkę; można oddzielnie objaśnić badania, bez twierdzenia, że protokół zapisano w Speediance. Tryb oporu pozostaje odrębnym wyborem i wymaga uzasadnienia dla konkretnego ruchu.

Producent opisuje funkcję jako stałą prędkość **lub** opór, więc nie potwierdza pomiarem stałej prędkości kątowej ani równoważności sprzętowej wszystkich generacji. Nie ma podstaw, by przenosić wyniki z dynamometrów izokinetycznych na GM. Producent nie publikuje recenzowanych badań porównujących te tryby na Gym Monster ani dowodu ich przewagi treningowej.

### Wybór treningowy a zapis przez klienta referencyjnego

Standard pozostaje podstawą. Tryb specjalny wybieraj tylko wtedy, gdy ćwiczenie, cel, preferencje, bezpieczeństwo i aktualne badania nad odpowiadającym mechanizmem to uzasadniają. Jeśli badanie dotyczy podobnego sprzętu, oznacz je jako dowód pośredni; nie twierdź, że przetestowano nim Speediance. Jeśli mechanizm lub wsparcie dla celu jest niejasne, wybierz Standard i wyjaśnij ograniczenie. Nie rotuj trybów bez powodu treningowego.

Aktywny kontrakt klienta referencyjnego dla własnych szablonów udostępnia trzy wartości Dynamic Weight: `1=Standard`, `2=Chain`, `3=Eccentric`. GM Coach przekazuje te wartości do `sportMode` bez remapowania. Zatem GM1 ma sprzętowy tryb Constant, ale bieżąca ścieżka zapisu klienta referencyjnego/MCP nie pozwala ustawić go w szablonie. W osobnym publicznym kliencie `speediance-cli` polecenie `push` ma inną enumę: `1=Standard`, `2=Eccentric`, `3=Isokinetic`, `4=Constant`, `5=Spotter`; nie wolno kopiować tych kodów do kontraktu klienta referencyjnego. W jego ścieżce kod `3` zawsze pozostaje Eccentric — nigdy nie Isokinetic. Tę różnicę opisują interfejsy klientów; same kody nie dowodzą, które opcje pokazuje konkretny ekran urządzenia.

Mimo że GM1 ma tryb Constant, aktywne narzędzie zewnętrzne udostępnia w zapisanym szablonie tylko trzy wartości Dynamic Weight. GM Coach nie zapisuje Constant/Fixed Speed ani Spotter przez kody 2/3 ani przez niezweryfikowane 4/5. Jeśli użytkownik prosi o Constant/Fixed Speed (czasem marketingowo „Isokinetic”) lub Spotter, powiedz, że aktualna integracja nie potrafi zapisać tego w szablonie; można wskazać ręczny wybór na urządzeniu tylko po potwierdzeniu widoczności opcji. Przy odczycie szablonu nazwij tylko rozpoznane kody 1–3; inne pokaż jako surowy, nierozpoznany kod zamiast przypisywać im nazwę z innego API.

Odczyt zwrotny potwierdza zapisane `sportMode`, nie fizyczne zachowanie silnika. Testy offline sprawdzają wyłącznie payload; fizyczne działanie trybu na maszynie nie jest potwierdzone. [Oficjalny FAQ Speediance — cztery tryby oporu i osobny Spotter](https://me.speediance.com/pages/faq) · [oficjalna strona oryginalnego Gym Monster — Constant](https://eu.speediance.com/en/pages/speediance-gym-monster) · [oficjalna strona GM3 — Fixed Speed i etykieta obrazu Isokinetic](https://eu.speediance.com/en/pages/speediance-gym-monster-3) · [publiczny kontrakt CLI z osobnym, niezgodnym enumem](https://github.com/stozo04/speediance-cli/blob/main/docs/MACHINE_CONTRACT.md).
## Granica programowania przez integrację

Historia treningów korzysta z własnego natywnego API GM Coach: listy `/mobile/v2/report/userTrainingDataRecord` oraz szczegółów właściwej przestrzeni `/app/trainingInfo/` dla rozpoznanego rodzaju sesji. Odczyt historii wymaga upoważnienia; zapis w kalendarzu nie jest wykonaną sesją. Katalog ćwiczeń i akcesoriów GM Coach pobiera bezpośrednio z endpointów biblioteki ćwiczeń Speediance, a wymagane akcesoria mapuje z pola `accessories` do nazw z globalnego `/app/accessories/list`. Katalog akcesoriów nie pokazuje własności. Presety i zapis programów wykorzystują reverse-engineered API. referencyjne ID celu 1/3/5 oznaczają Gain Muscle/Stamina/Strength; nie myl ich z ID grupy ćwiczenia ani `actionLibraryId`. Dla całej rodziny Gym Monster (`device_type=1`), obejmującej wszystkie jej generacje, te trzy presety pochodzą z globalnego menu klienta referencyjnego i są niezależne od wariantu ćwiczenia. Wariant potwierdź osobno w katalogu. Inne rodziny, w tym 2=Gym Pal i 3=Velonix, nie są obsługiwane przy zapisie programu ani planowaniu; 2 i 3 nie oznaczają generacji GM2 i GM3. Dla innych niepotwierdzonych ID presetów nie zgaduj mapowania nazwa–ID. Niejednoznaczne mapowanie blokuje zapis. To nie jest oficjalny, gwarantowany kontrakt Speediance i może się zmienić. [Kontrakt CLI](https://github.com/stozo04/speediance-cli/blob/main/docs/MACHINE_CONTRACT.md) · [publiczny builder presetów](https://github.com/ANPC86/SmartGymWorkoutManager/blob/main/api_client.py) · [README forku i testowane ID](https://github.com/ANPC86/SmartGymWorkoutManager).

Przed zapisem GM Coach pokazuje plan z ćwiczeniami, seriami, reps albo czasem, przerwami, kolejnością oraz dawką Smart RM albo jawnie wybranego `Customize`/fixed-kg. Nie pokazuj bezwzględnych kg/lb bez prośby. Zapis wymaga jawnej zgody użytkownika. Nowe serie oporowe na powtórzenia używają domyślnie maszynowego Smart RM; istniejący zapisany szablon zmienia się tylko po osobnej prośbie i zgodzie:

- nowe serie oporowe domyślnie zapisuj jako Smart RM z nazwanym presetem, reps i RIR jako osobnymi wartościami planu, oraz ukrytym adapterem RM klienta referencyjnego w `counterweight`/`counterweight2` i `weights=3.5`;
- statyczny klient referencyjny `Customize`/`profile-auto` wybieraj tylko po jawnej prośbie i z dokładną kotwicą oraz jednostką konta;
- ręczne stałe kg dobieraj tylko na wyraźną prośbę, z wartością dla każdej serii;
- nie zgaduj anchor, jednostki ani presetu; nie traktuj odczytu zwrotnego jako dowodu fizycznego działania urządzenia;
- jeśli preview/API zwraca `unit=unknown`, a użytkownik bezpośrednio potwierdzi jednostkę wyświetlania dla tego planu, przekaż dokładnie tę wartość jako `confirmedDisplayUnit` zarówno w preview, jak i identycznie w create. Wysyłaj pole tylko przy `unit=unknown`; jawna jednostka z API ma pierwszeństwo. Potwierdzenie dotyczy jednego planu i nie może być zapisywane w profilu;
- bezpieczne superserie GM Coach zapisuje jako naprzemienne wiersze serii i przerwy; endpoint nie ma osobnego ID grupy. Dropset, rest-pause i pauzy/tempo nie mają potwierdzonych pól wykonawczych; drop-set, reverse drop i rest-pause/klaster wolno zapisać tylko jako przybliżenie z wierszy serii (restSeconds 0–15/≤30 s, reps na wiersz), tempo i inne bez wierszy pozostają not_used; oddzielne omówienie naukowe nie jest instrukcją wykonawczą tego planu;
- `device_type=1` oznacza rodzinę Gym Monster, obejmującą jej generacje, a nie wyłącznie GM1. GM Coach odczytuje katalog i historię oraz zapisuje plany przez własne natywne API. Model i generacja nadal nie są automatycznie wykrywane; zgodność kontraktu API nie potwierdza fizycznego działania każdej generacji. GM Coach blokuje zapis programu i planowanie dla innych rodzin (`device_type != 1`); wartości 2 i 3 nie oznaczają GM2 i GM3.

Przy edycji istniejącego szablonu zachowaj jego `templatePresetId`, jeśli `groupId` i `actionLibraryId` pozostają identyczne, chyba że użytkownik wyraźnie żąda zmiany presetu zgodnej z celem. W całej rodzinie Gym Monster (`device_type=1`) takie żądanie może wybrać globalne ID klienta referencyjnego 1/3/5 niezależnie od wariantu; nowy wariant musi być potwierdzony w katalogu. Inne rodziny urządzeń nie są obsługiwane przy zapisie ani planowaniu. Dla innych, niepotwierdzonych presetów wymagaj jawnej mapy nazwa–ID z metadanych lub nazwanych programów. Wartość `templatePresetId=-1` nie wystarcza do ustalenia obciążenia: wraz z poprawnymi statycznymi weights i pustymi counterweight oznacza Customize; może także występować w poprawnej akcji bez RM. Rozpoznawaj pełne pola dawki, typu katalogowego i obciążenia; nie uznawaj samego -1 za brak ciężaru.

## Wykorzystanie pełni możliwości

„Pełne wykorzystanie GM” oznacza świadome użycie wszystkich potwierdzonych, przydatnych opcji danej osoby: katalogu ćwiczeń, rodzajów ruchów, dostępnych akcesoriów, regulacji stanowiska, funkcji aplikacji widocznych w urządzeniu, progresji i treningów z historii. Nie udawaj dostępu do żywego sterowania ani funkcji producenta niewystawionych przez aktualną integrację GM Coach.

# Odkrywanie fizycznej maszyny — ograniczenia źródeł (2026-10-08)

Odczyt publicznych klientów [klient referencyjny](https://raw.githubusercontent.com/hbui3/UnofficialSpeedianceWorkoutManager/main/api_client.py) i [gm-summary](https://raw.githubusercontent.com/pookey/gm-summary/main/speediance.py) nie ustalił kontraktu listy fizycznych maszyn konta. `device_type=1` oznacza konfigurację rodziny Gym Monster, nie wykrycie generacji. `device_type=2` nie jest dowodem GM2. Nagłówki Versioncode/User-Agent opisują klienta, nie firmware maszyny. Model, generacja i firmware pozostają nieznane bez potwierdzonego odczytu.

`owned_devices` i `owned_accessories` klienta referencyjnego są konfiguracją lokalną, a `accessories/list` katalogiem; żadne z nich nie dowodzi własności ani podłączenia akcesorium. [Polityka prywatności Speediance](https://ca.speediance.com/policies/privacy-policy) opisuje zbieranie identyfikatorów sprzętu, ale nie publikuje endpointu ani mapowania generacji. Nie zgaduj ścieżek API lub generacji z nazw treningów. Brak ustalonego kontraktu nie dowodzi nieistnienia endpointu.

Formularz logowania nie powinien wymagać wyboru generacji. Ujawniaj osobno skonfigurowaną rodzinę i brak potwierdzonego wykrycia modelu. Przyszły adapter wykrywania musi mieć potwierdzone żądanie, schemat i źródło oraz zachowywać przypadki zero/jedna/wiele maszyn i częściowe błędy; nie wybieraj pierwszej maszyny bez jednoznacznego powiązania celu.
